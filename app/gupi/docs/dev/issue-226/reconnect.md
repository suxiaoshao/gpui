# 手动刷新时重新连接 Pi

状态：已实现，待用户体验。2026-09-13 用户确认：刷新改为重新连接，以便加载修改后的扩展、skills、提示词等资源。

## 行为契约

- Cmd/Ctrl+R、顶栏刷新按钮和命令面板“刷新当前会话”使用同一入口：关闭当前会话的旧 Pi 连接，等待收尾后启动新进程，恢复同一会话并读取状态和历史。
- 仅影响目标会话。其他会话及其任务保持原有运行状态；不借此改变 Gupi 多实例所有权。
- 运行、压缩、重试、普通消息提交、待答扩展交互和其他会话写操作期间不启动重连；不把刷新变成隐式中止。键盘与鼠标使用同一门禁。
- 重连 task 由目标会话持有；期间显示 loading，禁止重复重连和冲突写操作。等待旧进程收尾后才交接新连接，避免同一文件出现两个 Gupi 写入实例。
- 保留已显示正文和未发送草稿；连接失败显示错误并允许重试，不清空会话、不跳到新对话。已落盘会话恢复原文件；已连接的空会话也允许重连，保留项目、草稿、当前模型与思考等级，不因配置默认值变化重置选择。
- 旧连接的待答请求、标题、status、widget 依照既有关闭规则清理；新进程事件按新的绑定身份接收，旧完成链不能覆盖新状态。
- 新实例的模型、思考、统计和命令列表等数据重新读取，不沿用旧实例缓存冒充已经更新。

## 与 TUI /reload 的边界

资源重新加载的使用目标一致，机制不同：TUI 在原进程中执行 session.reload，Gupi 退出旧进程并重新恢复会话。插件的临时内存与事件 reason 不会完全一致；不伪造 reload 事件，也不自行重建 Pi 资源加载规则。

Pi 的主题、键位或扩展资源重新读取，不表示 Gupi 会自动导入 Pi TUI 主题、keybindings.json 或 custom UI。Gupi 自身设置与快捷键继续由应用管理。

### 空对话的源码依据

Pi `interactive-mode.ts::handleReloadCommand` 只检查 streaming/compacting，没有消息数量、sessionFile 或落盘门禁。`AgentSession.reload` 在原 AgentSession 上重建资源和扩展绑定，保留 SessionManager 与 Agent 的模型/思考状态，不重新执行默认模型选择。扩展 reload 钩子仍可按其业务修改状态，不能保证所有插件都不改变模型。

因此 Gupi 对已连接空会话使用同一刷新入口，无须先发送消息。重连启动前保留旧实例实际模型和思考值，包括初始默认选择；恢复不能只保护“用户手动改过”的值。按原生启动/恢复能力传递这些选择，优先在启动钩子前恢复；必要读取与失败处理见决定清单中的技术核验项。

从未连接的本地空草稿没有已加载的 Pi 资源，TUI 中没有这个前置状态；首次连接时机见 C-11，不把刷新当成第二条并发初始化入口。尚在首次连接时不重复重连。未落盘空会话重启后 Pi 的内存会话 ID、尚未持久化的内部条目和插件内存不能承诺与进程内 reload 完全相同；Gupi 保留本地页面归属、草稿及模型/思考选择，不自行构造 session 文件来模拟同一进程。

内部 `ConversationState::refresh` 有消息完成、操作结束等多个调用方，继续作为轻量 get_state/get_entries 回读。新增明确的手动重连入口，不把现有 refresh 全局替换成进程重启。目录刷新和模型弹层中的数据刷新也不附带重启。

## 现有实现与复用边界

- `ConversationState::close` 已持有 Closing task，关闭前递增 binding、重置读资源和扩展 UI；`PiState::close` 返回持有连接及事件消费者的 task，等待 client.close 完成。
- `CloseReport.status` 仅在观察到退出时为 Some；已有 deletion 流程在 status 缺失时停止文件操作。重连复用这一退出确认边界，不把“已请求关闭”当作可启动第二个写实例的证据。
- 现有 close/launch 会清空 state、reset_reads；直接串联调用无法完整表达“旧正文仍显示但不可写”“等待恢复”和整个重连的完成状态，需要由会话操作持续持有过程。
- PiState 继续管理进程；ConversationState 管理来源文件、草稿和业务门禁。采用一个会话操作 task/状态表达重连，不并列增加多个缺少统一 owner 的 is_reconnecting 布尔值或自制后台进程管理器。

## 顺序与完成条件

| 阶段 | 必须完成的工作 | 下一步条件 |
| --- | --- | --- |
| 接受操作 | 校验当前 key/绑定、忙碌状态、来源文件；保留显示快照、草稿与必要会话选择信息，进入重连操作 | 不是简单把旧 connection 标成空闲 |
| 关闭旧连接 | 旧 binding 失效，清理旧资源 UI，等待既有关闭流程；保留原正文投影供阅读 | 有退出确认后再启动；status 缺失时反馈错误，不在同一操作里盲目重试拉起 |
| 启动与恢复 | 用原 cwd 和真实已落盘 session 路径启动；已知历史沿用文件身份校验；无旧连接时可直接走恢复 | ready、核心 snapshot 完成并确认目标身份 |
| 核对会话选择 | 启动前保留当前模型/档位，按启动/恢复顺序传递并读取结果；不在扩展钩子后无条件覆盖其修改 | 核心可用，选择状态已确定，才能恢复普通发送 |
| 附加数据 | 重读统计、模型/思考候选、fork 候选和需要展示的命令列表 | 各自保留失败重试，不因命令列表失败判整个会话不可用 |

“重连完成”指核心会话恢复和必要选择恢复完成，不等待所有附加列表加载结束。连接成功后模型列表或 get_commands 失败只在相应区域反馈，不能通过重启进程反复尝试附加查询。

## 状态交错与失败

- 用户切换到其他会话时，目标操作仍属于原 key；完成不强制切回来。新会话沿用已有行为，不能因当前视图离开就让旧进程关闭停在半途。
- 首次连接和重连期间，直到连接及初始状态读取就绪，目标会话的主输入框只读并保留原文，禁止发送、模型修改、fork、改名、删除和重复刷新。已断开的历史会话仍可重试连接；核心读取失败时保留现有连接并重试读取。
- 旧进程退出但新进程启动失败：原正文/草稿仍显示，明确连接失败，可再次尝试恢复；不回滚到已经退出的连接。
- 核心 snapshot 失败但新连接仍在：保留该新连接和普通读取重试路径；再次读取不能再次误建第二个实例。
- 文件被外部删除/替换时沿用现有身份校验报错，不创建新空会话替代历史文件。仅有模型选择、尚未实际落盘的空会话按上述规则重连，不能误报历史丢失。
- 应用退出时以 draining 阻止关闭后的新启动，操作 task 与 PiState 的现有退出收尾协作。不添加外部进程监控、信号重试或推测性的 RAII 修复。

## 最小验收矩阵

| 情况 | 需要的证据 |
| --- | --- |
| 已落盘会话正常重连 | 可控进程记录旧退出先于新启动；恢复同一 ID/文件；原草稿保留 |
| 其他会话仍运行 | 重连只影响来源实例，其他连接与事件继续有效 |
| 旧进程关闭无法确认 / 新启动失败 | 不重叠启动；错误可见；不清空正文与草稿 |
| 旧事件/读结果迟到 | 旧 binding 不覆盖新数据，旧插件状态不复活 |
| 核心恢复成功但附加读取失败 | 普通会话可用，对应资源能独立重试 |
| 空会话重连 | 无消息/无实际文件仍能刷新，当前模型与思考值不被新配置默认值重置；首次连接中不重复拉起实例 |
| 重连中退出应用 | 不在 draining 后启动 Pi，沿用原有收尾 |

这些检查聚焦本次新的跨进程交接，不重新审计 Pi agent 任务取消。操作确认和平台展示仅做必要检查，临时 gallery 仍由用户自行体验。
