# Issue #182：`gpui::View` 迁移判断标准

## 状态与边界

- 状态：`草稿`
- 跟踪 issue：[#182](https://github.com/suxiaoshao/gpui/issues/182)
- 根文档：[README.md](README.md)
- 候选清单：[view-migration-inventory.md](view-migration-inventory.md)
- 范围：定义后续工作区审计如何判断一个可渲染边界是否应迁移为直接实现 `gpui::View`。
- 不包含：候选清单、受影响所有者映射、工作包、实现，或对上游依赖的修改。

本文档是 issue #182 的规范性适用性判断标准。后续候选清单必须将本标准应用于届时最新的工作区，而不能把任何当前组件列表视为冻结的范围。

## 框架基线

工作区当前将 GPUI `0.2.2` 锁定在 Zed 提交
[`1a246efd`](https://github.com/zed-industries/zed/blob/1a246efd7e1b83ab568ec5e3e6c1a43a42e1abba/crates/gpui/src/view.rs#L171-L221)。
在此版本中：

- `View` 是 `Render` 和 `RenderOnce` 背后的通用响应式渲染模型。
- `Entity<T: Render>` 已经使用自身的 `EntityId` 实现了 `View`。
- `T: RenderOnce` 已经在没有实体标识的情况下实现了 `View`。
- 直接实现 `View` 适用于把父级提供的渲染时属性与稳定后备实体结合起来的混合场景。
- `View` 的实体标识限定了内部元素状态的作用域，并使来自该实体的通知重新渲染该 `View` 子树。

因此，本次迁移不是机械地替换 trait。它要纠正现有形态中的所有权问题：这些形态隐藏或重复了父级拥有的属性与组件持久状态之间的区别。

## 规范性决策

当一个可渲染边界同时具备以下两项时，应迁移为直接实现 `View`：

1. 拥有标识以及真正持久的交互或生命周期状态的稳定后备实体；以及
2. 应当在父级每次渲染时重新提供的、由父级拥有或从父级派生的输入。

当前采用的 trait 或函数形态并不是所有权的权威证据。由于过去不存在直接实现 `View` 的能力，历史代码可能被迫写成实体、函数或 `RenderOnce` 构建器。

对于 issue #182，直接实现 `View` 必须返回 `Some(backing_entity.entity_id())`。应当返回 `None` 的可渲染对象继续使用 `RenderOnce`。

## 渲染模型选择

| 语义形态 | 必须采用的模型 |
| --- | --- |
| 无持久标识或内部状态的无状态、一次性组合 | `RenderOnce` 或局部渲染辅助函数 |
| 稳定后备实体加父级提供的渲染时属性 | 直接实现 `View` |
| 长生命周期控制器，其状态、任务、订阅和事件协调仍由实体整体拥有，且无法与渲染属性分离 | `Entity<T: Render>` |
| 底层自定义布局、`prepaint` 或 `paint` 原语 | `Element` |

任何类型都不会仅仅因为当前包含一个 `Entity` 就迁移。反过来，任何类型也不会仅仅因为当前是函数、`RenderOnce` 或完全由实体拥有的 `Render` 组件而被排除。

## 候选发现范围

后续审计必须检查所有可渲染边界，而不只是 `impl Render` 声明：

1. `Entity<T: Render>` 组件。
2. 持有 `Entity<_>` 或 `WeakEntity<_>` 的 `RenderOnce` 或 `IntoElement` 结构体。
3. 构造函数会克隆实体句柄、配置方法消费并返回 `Self` 的构建器风格结构体。
4. 返回 `impl IntoElement`、`AnyElement` 或其他可复用渲染结果的自由函数和关联方法。
5. 在渲染前把父级或领域状态写入子实体的适配器或包装器。
6. 目的可能是镜像权威数据的父子订阅、观察器、设置器、重新基准化、投影替换和 `sync_*` 路径。

这些形态会进入审计，但不会自动获准迁移。每一个都必须根据所有权、标识和更新方向进行分类。

## 字段所有权分类

每个候选在选择渲染模型前都必须对其数据进行分类。

| 数据种类 | 权威来源 | 目标位置与更新规则 |
| --- | --- | --- |
| 领域值或表单值 | 领域或表单所有者 | 由父级边界提供或引用；提交和验证不得把组件缓存视为权威来源 |
| 父级派生的展示、标签、启用状态、样式、尺寸、变体、无障碍元数据、回调、前缀/后缀或目录策略 | 父级或应用所有者 | 作为临时 `View` 上的普通字段；在父级渲染期间重建 `View` 来刷新 |
| 焦点、打开状态、查询、高亮、选择机制、光标、滚动、IME、局部编辑状态或瞬时交互状态 | 组件 | 稳定的后备 `Entity<State>` |
| 任务、订阅、保留的句柄，以及取消或生命周期状态 | 组件或控制器 | 稳定的后备实体或独立拥有的嵌套实体；绝不能放在临时 `View` 值中 |
| 嵌套控件状态 | 嵌套控件 | 只有在其具有独立标识、交互状态或生命周期时才保留嵌套实体 |
| 延迟处理程序配置 | 对每个字段明确确定 | 优先在处理程序中捕获当前属性；仅当延迟行为确实需要快照，并且其权威来源和更新方向已有文档记录时，才保留状态快照 |
| 同时由父级和子级写入的值 | 未解决 | 停止分类，直到选定唯一权威来源和明确的投影或更新方向 |

当前在物理上共享同一个实体，并不意味着这些值属于同一个所有权通道。

## 隐藏的实体候选与父子同步

有些组件之所以被实现成完全由实体拥有，只是因为过去 `Render` 要求可渲染组件自身必须是实体。它们现在可能看起来是有状态的，但其中一部分状态其实只是父级的镜像。

以下情况是强烈的迁移信号：

- 每当父级权威数据变化时，父级都必须调用 `child.update(...)`、`set_*`、`sync_*`、`rebase_*` 或等效命令；
- 某个子级字段只由父级写入，并且只用于展示；
- 某个订阅或观察器主要用于把父级或领域值复制到子级状态；
- 父级计算一个值，把同一个值存进子实体，然后再渲染子级；
- 组件设置器的存在仅仅是为了让父级拥有的标签、启用状态、回调、选项、样式或其他属性保持最新；
- 移除这些镜像字段后，子实体仍然保有清晰的交互状态和标识。

即使这些组件当前的类型形态无法让人一眼看出是否适合迁移，也必须进入迁移清单。

当审计确认实体所有权和父子同步的存在，仅仅是因为过去无法直接实现 `View`，所以需要镜像父级拥有的渲染输入时，必须将其分类为迁移到 `View`。这种偶然形成的实体形态不是保留该所有权的理由。

迁移应当在明确每个受影响字段的权威来源和更新方向之后，删除已经过时的镜像字段和同步路径。如果拟议的 `View` 仍然需要相同的父到子镜像，那么所有权纠正尚未完成。

## 函数形式的组件

函数不一定是无状态的，也不得在审计中遗漏。

当函数符合以下条件时保留函数形式：

- 它是某一个所属渲染边界内部的私有拆分辅助函数；
- 它没有独立标识或持久状态；
- 它只根据参数和当前应用状态生成输出；并且
- 它不会把这些参数同步进子实体。

当函数形式的边界符合以下条件时，将其转换为具名 `View` 类型：

- 它代表具有独立稳定标识的可复用子组件；
- 它接受或查找到一个稳定实体，同时还接收父级提供的属性；
- 它需要 `use_state`、有状态的元素 ID、焦点、弹出层、选择、滚动或其他限定在标识作用域内的行为；
- 它仅仅为了在渲染前同步函数参数而修改实体；或
- 它以其他方式实现了“后备实体加临时属性”的语义形态。

生成的具名类型可以保留构造函数和构建器方法。创建具名 `View` 必须增加一个真正的所有权或响应式边界，不能只是包裹一个纯辅助函数。

## 实体句柄构建器组件

以 `gpui-component::Input` 为模型的构建器组件必须纳入审计。当前依赖在
[`57a9903f`](https://github.com/longbridge/gpui-component/blob/57a9903f48160845aabc8b92a1e2f5348c80d439/crates/ui/src/input/input.rs#L35-L184)
中展示了这种形态：

- `new(&Entity<State>)` 克隆一个稳定的实体句柄；
- `.disabled(...)` 等配置方法消费并返回 `Self`；
- 临时组件值同时持有稳定状态句柄和渲染时配置。

克隆一个 `Entity<State>` 句柄是预期行为，它不会克隆底层状态。把父级或领域值克隆到长生命周期的子级字段中属于另一个所有权问题，并且可能是同步异味。

当构建器风格类型符合以下条件时，应迁移为 `View`：

- 被克隆的实体句柄是组件的稳定标识；
- 构建器字段是父级提供的渲染时属性；
- 持久的交互或生命周期状态仍保留在实体中；并且
- 组件使用当前属性重建，但不会重建实体。

在渲染期间把构建器属性写入自身实体的 `RenderOnce` 构建器是一个强烈的审计信号。审计必须判断这些写入是已经过时的镜像，还是某个延迟交互确实需要一个所有权明确的快照。仅有构建器语法并不足以迁移：真正无状态的构建器继续使用 `RenderOnce`。

`gpui-component` 只用于证明实现形态。issue #182 不授权修改依赖源码。

## 直接实现 `View` 的适用性门槛

候选只有通过所有适用门槛时才迁移：

1. **稳定标识：** 一个后备实体在父级重新渲染后继续存活，并提供 `EntityId`。
2. **有意义的渲染时属性：** 至少有一个输入由父级拥有或派生，不应成为持久子级状态。
3. **持久状态隔离：** 临时 `View` 重建后，所有交互状态和生命周期状态仍然存续。
4. **父级更新路径：** 父级属性变化会可靠地触发父级渲染并重建 `View`；展示数据不需要使用子级设置器。
5. **内部更新路径：** 内部修改会更新正确的后备实体或嵌套实体，并通知重新渲染受影响 UI 所需的响应式所有者。
6. **标识唯一性：** 同一父级作用域中的兄弟 `View` 不会使用同一个后备 `EntityId`；限定在标识作用域内的 `use_state`、元素状态和滚动状态不能发生冲突。
7. **不在渲染时创建实体：** 渲染或重建 `View` 绝不会重建后备实体、任务或订阅。
8. **减少同步：** 迁移会删除偶然形成的镜像或同步，而不是增加新的双向状态流。
9. **行为保持：** 焦点、选择、弹出层、验证、禁用状态、无障碍、事件，以及取消或生命周期行为都仍可测试且保持不变，除非另有说明。

如果无法从当前代码中确认某个门槛，应将候选分类为未解决，而不是猜测它应该迁移。

## 应保留现有模型的情况

当边界确实是无状态且一次性的，保留 `RenderOnce` 或函数形式。

当符合以下情况时，保留 `Entity<T: Render>`：

- 类型本身是一个内聚的长生命周期控制器；
- 它拥有无法清晰拆分成后备状态和渲染时属性的任务、订阅、事件和可变状态；
- 它没有有意义的父级提供的渲染时属性；
- `View` 包装器只会转发同一个实体，既不能删除同步，也不能澄清所有权；或
- 它的标识所有者或通知所有者会变得不明确。

在以下情况下不要迁移：

- 后备实体会在每次渲染时创建；
- 临时 `View` 会持有持久任务、订阅或可变状态；
- 父级属性变化无法可靠地重建 `View`；
- 在同一父级作用域中，一个后备标识必须被渲染成多个兄弟节点；
- 拆分需要更多快照、设置器、重新基准化或双向同步；或
- 直接实现的 `View` 会返回 `None`，而不是使用 `RenderOnce`。

## 后续每项决策所需的证据

后续候选清单必须为每个已审计边界记录：

- 当前渲染形态；
- 父级或领域拥有的输入；
- 组件拥有的交互和生命周期状态；
- 当前父到子和子到父的更新路径；
- 选定的后备标识，以及它在每个渲染位置是否唯一；
- 内部修改的通知所有者；
- 被删除或明确保留的同步路径；
- 最终分类：迁移到 `View`、保留 `Render`、保留 `RenderOnce`/函数，或未解决；
- 此分类所需的针对性验证。

对于已迁移组件，验证必须证明：

- 后备状态在父级重新渲染后仍然存续；
- 父级属性无需显式子级同步即可更新；
- 内部状态修改会通知并重新渲染预期子树；
- 兄弟节点的标识不会发生冲突；并且
- 现有的焦点、选择、弹出层、验证、禁用、无障碍、事件和生命周期行为得以保持。
